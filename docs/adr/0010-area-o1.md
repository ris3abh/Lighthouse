# 0010. The name is Area O1

- Status: accepted
- Date: 2026-10-07
- Phase: before Part E

## Context

"Lighthouse" is a common name: crowded on PyPI and GitHub, and it says nothing about O-1 or EB-1 cases. The
owner chose **Area O1** (letter O, not zero). A rename touches the package, the command, environment variables,
the keychain, user and workspace files, the UI, the docs and the installers, and people already have
Lighthouse-era workspaces that must keep working.

## Decision

### 1. One place for every name

`areao1/names.json` holds every name the product uses. Python reads it through `areao1/names.py`, the web app
imports it, and a test checks that the files that can't import it (installers, workflows, `pyproject.toml`, the
landing page, `CITATION.cff`) agree with it. A future rename edits that file and follows the failing tests.

| What | Name |
|---|---|
| Product | Area O1 |
| Python package and import | `areao1` |
| Command | `areao1` (`lighthouse-gc` stays as a deprecated alias that says the new name, then runs) |
| MCP server | `areao1` |
| Environment variables | `AREAO1_*` (for example `AREAO1_HOME`, `AREAO1_MODEL_HARD`) |
| Keychain service | `areao1` |
| User config folder | `~/.config/areao1` (`%APPDATA%\areao1` on Windows) |
| Workspace config / state | `areao1.yaml`, `.areao1/` |
| Default workspace for new installs | `~/AreaO1` |
| Request header the server requires on writes | `X-AreaO1` |

Not renamed: CHANGELOG history, accepted ADRs (they record what was decided then), and internal identifiers
nobody sees (the `lh-` CSS and browser-storage prefixes).

### 2. Lighthouse-era setups keep working

On the first run of the new version, once, with a one-line notice:

- The user config folder `lighthouse-gc` is copied to `areao1` (the remembered workspace goes with it).
- In a workspace, `lighthouse.yaml` becomes `areao1.yaml`, `.lighthouse/` becomes `.areao1/`, and the
  workspace `.gitignore` is updated to match. Nothing else in the workspace changes; a workspace remembered at
  `~/Lighthouse` stays there.
- A secret not found under the `areao1` keychain service is read from `lighthouse-gc` and copied over.
- `LIGHTHOUSE_GC_*` and `LIGHTHOUSE_MODEL_*` variables are still read when the `AREAO1_*` one isn't set, with a
  notice naming the new variable.
- The server accepts the old `X-Lighthouse` header too, so a tab left open across the upgrade still saves.

A test builds a Lighthouse-era workspace (old config file, old state folder, old keychain entry, old user config,
old environment variables) and checks that everything is found and moved, and that a second run moves nothing.

### 3. Not published yet

Nothing goes to PyPI until the owner says so. The owner renames the GitHub repository (GitHub redirects the old
URLs), reserves `areao1` and `area01` on PyPI, and decides on domains.

### 4. A little banter, on a short leash

A few lines of humor, only where the owner listed them (landing page hero and taglines, the footer, profile
switch labels and the first switch to EB-1A, the empty Inbox, the constellation loading line, a criterion
turning banked, the onboarding finish, opportunity notifications, the 404 page). Each is tagged in one
registry (`web/src/lib/banter.ts`, plus the Python strings for notifications), and tests enforce:

- **No banter on serious screens**: deadlines and countdowns, rule-check warnings, conflicts, refusals, errors
  other than 404, and anything about case status, RFEs or filing. Serious surfaces are marked
  `data-serious`; a tagged line never renders inside one or on a screen showing one.
- **"Alien"** is used only about us or in the legal term ("alien of extraordinary ability"), never as a label for
  the person.
- **Never mock** USCIS, attorneys or other companies.
- **At most one banter line per screen.**

The profile switch labels ("Visitor mode (O-1A)", "Resident mode (EB-1A)") are control labels that keep the legal
names in them; they show wherever the switch does, and count as names, not banter lines.

## Consequences

- Every user-facing string, command and path changes once; the tests make the next rename mechanical.
- Old commands, variables, keychain entries and files keep working for at least one release, with notices.
- The installers point at the new repository name, so they work only after the GitHub rename (GitHub's redirect
  covers the old URLs, not the new ones before the rename).
