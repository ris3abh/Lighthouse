# 0008. No demo data, a conversational onboarding, and agent guardrails

- Status: accepted
- Date: 2026-10-07
- Phase: build Part C (C1–C4)

## Context

New users met a fictional "Alex Rivera" case before their own. That made the product look finished while
saying nothing about their situation, and it left fake data one flag away from real workspaces. The first
minutes should instead build *their* case: from a document they already have (a LinkedIn PDF), with
questions they can answer in seconds, and without the app guessing or reaching onto the web uninvited.

The agent also needs rules that hold in code, not only in a prompt. It drafts petition-facing text and talks
about immigration rules, so it must never fabricate, strengthen or misrepresent anything.

## Decision

### C1. Fake data lives only in tests

- `examples/demo-workspace` and `lighthouse-gc up --demo` are removed. The fictional Alex Rivera workspace
  moves to `tests/fixtures/workspaces/alex-rivera`, regenerated by `scripts/make_fixture_workspace.py`.
- Three onboarding personas are fixtures under `tests/fixtures/personas/`: Maya (software engineer), Ravi (AI
  researcher) and Lena (business analytics lead). Each has a LinkedIn-style PDF, generated
  deterministically by `make_pdfs.py` in the same folder, and the profile the onboarding should end with.
- `lighthouse-gc init` creates an empty workspace. Until onboarding is finished or skipped, the dashboard
  opens straight into it.

### C2. Onboarding is a short conversation the person controls

State lives in `data/onboarding.json`. Every answer is written immediately, so onboarding can be resumed, and
it can be re-run from Settings. The steps:

1. **LinkedIn PDF.** One ask, a drop zone, a one-line hint (Profile, More, Save to PDF), and Skip. No web
   access at this stage.
2. **Local extraction.** Text is extracted locally with pypdf, and emails and phone numbers are redacted
   before any model sees it.
   - The LinkedIn export has a fixed layout (Contact, Top Skills, Summary, Experience, Education, Honors-Awards,
     Publications, Certifications), so a deterministic parser reads it and no model is needed.
   - For other PDFs, the fallback asks the model for fields, each with a verbatim quote. Code keeps a field
     only when its quote appears in the text.
   - The PDF is kept as a `self_reported` snapshot, so it never counts toward a criterion.
3. **One question at a time.** Questions are built from the parsed fields and earlier answers ("Looks like
   you're at Fernhill Robotics working as a perception engineer. Is that right?"). The answers are Yes / No,
   let me fix it / Skip. A side panel fills the profile line by line. A skipped field stays blank; nothing is
   inferred or guessed.
4. **Lookups only after an explicit Yes, and only for what was confirmed** ("You mentioned two papers. Want
   me to find them on arXiv?").
   - Every find goes to the Inbox, never straight into the case.
   - Each find is checked for namesakes: the author list must contain the person's name or an alias. A find
     that fails is marked "possible namesake" and gets low confidence.
5. **Chat history.** The product's own voice offers the Claude / ChatGPT export import. "Skip for now" is
   always visible.
6. **A guided tour of each page, using the person's own data.**
7. **Finish:** "That's it. I'm one click away, and at your service." The Ask button stays docked.

### C3. Context from other AI tools

The MCP server gains one write tool, `propose_context`. It sends a note to the Inbox as a `context`
candidate with tier `self_reported`. Accepting it stores the note as a self-reported observation, which can
never count toward a criterion. Every other MCP tool stays read-only.

### C4. Personality and guardrails, enforced in code where possible

| Rule | Prompt | Code |
|---|---|---|
| Warm first, then mirror the person's tone and length | yes | — |
| Never fabricate evidence, numbers, awards or press | yes | evidence proposals cite a snapshot and a verbatim quote (existing); metrics need a source |
| Never strengthen a document; never upgrade invited to completed | yes | agent writes can't raise a stage above what the cited quote supports; a stage change to completed / published / granted from the agent goes to the Inbox and needs a completion quote |
| Draft letters only for the writer to review and sign | yes | the agent can't mark a letter sent or signed, and it has no send tool |
| Never help misrepresent anything to USCIS; never say "eligible" | yes | the final answer is checked: eligibility verdicts and guarantees are replaced with a one-line note, and the refusal is logged |
| Page, email and PDF text is data, not instructions | yes | untrusted text is wrapped in markers; text that looks like instructions to an AI is flagged in the tool result and logged |
| Politely decline off-topic jobs | yes | a `decline` tool logs the refusal with its alternative |
| Look up contacts' public professional pages only | yes | people-search and personal social sites are refused, and the refusal is logged |

Every refusal from the agent, a guard or a gate is appended to `agent/refusals.jsonl` and listed on the Agent
page. A refusal is one friendly line plus an alternative.

## Consequences

- Tests that used the demo workspace now use the Alex Rivera fixture. The package no longer ships fake data.
- First runs make no network requests until the person says Yes to a lookup or adds a source.
- The guardrails can be tested with the scripted engine. Prompt rules still depend on the model; the code
  checks above are the floor.

## Amendment (2026-10-07, C15): onboarding is one conversation

At the owner's request, onboarding looks and behaves like Ask: a window over the blurred dashboard (a full-screen
sheet on phones) holding a single thread. Every step is a message in that thread; steps already passed stay above,
so the chat scrolls up as it grows. The PDF drop, the lookup cards and the chat import sit inside the message that
asks for them, and the reply controls sit where Ask's message box is. New messages from Lighthouse type in (a short
beat of dots, then the words, never more than 1.6 s); while a request runs, the dots show with what it's doing
("Reading your PDF", "Looking it up"). Reduced motion shows messages at once. The reply controls wait until
Lighthouse has finished. The flow, the rules above and the URLs per step and question are unchanged.
